# Architecture

## Stack (as actually implemented so far)

- **Frontend**: Next.js 14 (App Router), React 18, TypeScript, Tailwind CSS.
  Client-side auth context stores the JWT access token in `localStorage`
  and attaches it as a Bearer token. This is adequate for development but
  should move to httpOnly cookies (with CSRF protection) before handling
  real customer data in production — tracked in docs/CHECKLIST.md.
- **Backend**: FastAPI, SQLAlchemy 2.0 (async), Pydantic v2, Alembic
  migrations, pytest + httpx for testing.
- **Database**: SQLite for local dev/tests (zero setup), Postgres in
  staging/production via `DATABASE_URL`. The same SQLAlchemy models and
  Alembic migrations target both.
- **Auth**: Email + password, bcrypt hashing (passlib), JWT access
  (30 min) + refresh (14 day) tokens, HS256. No email verification
  delivery, OAuth/SSO, or MFA yet.
- **Multi-tenancy model**:
  - `User` — an account.
  - `Organization` — a billable/shared tenant.
  - `Membership` — join table (`user_id`, `organization_id`, `role`), role
    is one of `owner`, `administrator`, `analyst`, `viewer`, `auditor`.
  - `Workspace` — owned by exactly one of: a single user (`owner_user_id`,
    a "personal" workspace) or an organization (`organization_id`, a
    "shared" workspace). Access to an org workspace requires an active
    membership row; this is enforced server-side in
    `apps/api/app/services/authz.py`, not just in the UI.

## Why these choices

- **Modular monolith, not microservices** — per the brief's explicit
  instruction to avoid unnecessary complexity. The API is a single
  deployable; background workers (for file processing, in Phase 2) will
  be a separate process reading from the same codebase, talking to Redis
  as a queue — not a separate service with its own API.
- **SQLite for dev/test, Postgres for prod** — keeps the test suite fast
  and dependency-free (no Docker required to run `pytest`) while the
  production path uses a real, horizontally-scalable database. All models
  avoid Postgres-only or SQLite-only column types to keep this safe;
  revisit if a future migration needs a Postgres-specific feature (e.g.
  native ENUM, JSONB).
- **Alembic migrations are the only way the schema changes.** Autogenerate
  was used to produce the initial migration; review every future
  autogenerated migration by hand before applying it — autogenerate does
  not reliably detect every kind of change (renames, some constraint
  changes).

## Phase 2 additions: dataset storage model

- `Dataset` (a named, long-lived thing in a workspace) → `DatasetVersion`
  (one upload, or one applied cleaning operation) → `DatasetTable` (one
  per worksheet). Versions are immutable once created: a cleaning
  operation reads a version and writes a *new* version rather than
  mutating it, so "the original dataset must remain recoverable" (the
  brief's requirement) falls out of the data model rather than needing
  separate backup logic.
- Each `DatasetTable.profile` is a JSON blob (schema + stats + quality
  issues), not a normalized set of tables — an intentional Phase 2
  simplification. The brief's full "Data quality results" /
  "Transformations" table list (section 16) will likely want this
  normalized once querying/filtering across many datasets' issues
  becomes a real feature; revisit then, don't prematurely normalize now.
- `Transformation` is the audit trail: source version, result version,
  operation type, parameters, who did it, when. Only `deduplicate` writes
  one today; the model doesn't need to change as more operations are
  added.
- Object storage is abstracted the same way the database is: a
  zero-setup local-disk default for dev/tests, a real S3-compatible
  (boto3) backend that activates once `S3_ACCESS_KEY` is set. Unlike the
  database, the S3 path hasn't actually been run against a real bucket
  yet — see docs/CHECKLIST.md.
- Upload processing runs in a FastAPI `BackgroundTasks` callback, not
  inside the request: the upload response returns as soon as the file
  is validated and stored, and parsing/profiling happen afterward in
  the same process. A deliberate lightweight choice over a real job
  queue — no separate worker process, no job-status API beyond the
  existing `DatasetVersion.status` field, and the frontend polls that
  same dataset-detail endpoint it already had. Redis is still
  provisioned in docker-compose but unused; a heavier queue (Celery/RQ)
  would be the next step if a single-process background task stops
  being enough. See docs/CHECKLIST.md's "Post-Phase-7: async upload
  processing (background task)" section.

## Phase 4 additions: billing and entitlements

- `app/core/plans.py` is the single configurable registry of plan limits
  — nothing else in the codebase hardcodes a quota number. Quota checks
  (`app/services/billing.py`) read it directly; changing a limit is a
  one-line edit there, no migration or route change needed.
- `Subscription` mirrors `Workspace`'s personal-vs-organization split
  (exactly one of `owner_user_id` / `organization_id` set) and is
  created lazily on first access, always on the Free plan — there is no
  "account with no subscription" state anywhere else in the app to
  special-case.
- `UsageCounter` is the only *metered* quota (monthly analyses) — file
  size and saved-dataset-count are point-in-time checks against live
  data (`len(content)`, a `COUNT(*)` query), not counters, so they don't
  need their own row and can't drift out of sync with reality.
- Two dependency-ordering bugs of the identical shape were caught in
  this phase and in Phase 3: a FastAPI route with both an authorization
  dependency and a "is this external service configured" dependency
  must declare the authorization one *first* in its signature —
  `Depends()` params resolve in signature order and stop at the first
  exception, so the wrong order lets an unauthorized caller learn
  "Stripe/the LLM isn't configured" before ever being told "no." Both
  ai_analyst.py and billing.py now have a regression test asserting
  403-before-503. Worth checking for the same pattern in any future
  router that mixes auth checks with external-service gating.
- Stripe webhook signature verification (`stripe.Webhook.construct_event`)
  is a pure local HMAC computation — it needs the webhook secret, not a
  live Stripe connection. That's what makes
  `tests/test_billing_webhook.py` possible without a real account: the
  test signs its own payloads with a secret it set via env var, using
  Stripe's publicly documented signing scheme, and sends them through
  the real verification code.

## Phase 5 additions: industry packs

- `app/core/industry_packs.py` is the registry (same pattern as
  `plans.py`/`tools.py`): each pack defines canonical fields with their
  real-world column-name aliases, KPI definitions, suggested questions,
  terminology, and (for social housing) a compliance caveat that's
  enforced to always appear alongside that pack's results — not just
  documented as a policy.
- Column matching (`app/services/industry_matching.py`) is deliberately
  two-pass: exact normalized match first, then whole-word-token subset
  matching as a fallback — never raw substring matching, which would
  false-positive ("Parent Company" containing "rent"). It's a heuristic,
  not a certified parser; there's no review/correction UI yet for when
  it gets a mapping wrong (Phase 2's schema-confirmation screen is the
  natural model to extend here).
- The KPI engine (`app/services/industry_kpis.py`) reuses
  `analytics.py`'s date-parsing helper rather than reimplementing it, and
  every KPI is independently reported with its own `error` field when
  its required columns aren't mapped — a table missing `lease_end_date`
  still gets `total_rent_roll` computed, it just can't compute
  `leases_expiring_12_months`. Partial data degrades gracefully instead
  of failing the whole request.
- The one built specialist report (`generate_commercial_property_report_pdf`
  in `app/services/reports.py`) and the `/industry-kpis` API endpoint
  call the exact same KPI functions — there's no second, parallel
  calculation path that could silently drift out of sync with the first.
- A KPI defined in a pack but missing from `_CALCULATORS` fails silently
  per-KPI (returns "No calculator implemented yet." in its `error`
  field) rather than crashing the whole request — a deliberate choice so
  one broken KPI doesn't take down the rest, but it also means a missing
  calculator (as happened once during this build — see
  docs/CHECKLIST.md) produces no loud error anywhere. The regression
  test added after that bug (`test_every_pack_kpi_has_a_registered_calculator`)
  is the real safety net, not the error field — keep it passing.

## Phase 6 additions: dashboards and scheduling

- `Dashboard`/`DashboardWidget` store only widget *configuration*
  (`{"kpi_id": ...}` or `{"operation": ..., "parameters": ...}`) — never
  a computed value. Every read recomputes from the live Parquet data
  through the same `TOOLS` registry and KPI engine that `/analyze` and
  `/industry-kpis` use directly, so a dashboard is structurally
  incapable of showing a stale or disagreeing number. The cost is that
  rendering an N-widget dashboard does N live computations on every
  view — fine at today's scale (all deterministic, in-memory Polars
  operations over one table), worth revisiting if dashboards grow to
  hold dozens of widgets or very large tables.
- Scenario modeling (`app/services/scenario.py`) deliberately does not
  introduce a second metrics pipeline: it mutates a cloned DataFrame and
  feeds it through `compute_kpis` a second time. This means every new
  KPI added to a pack automatically becomes scenario-modelable with zero
  additional code — the alternative (a parallel scenario-specific
  calculation path) would need to be kept in sync by hand forever.
- The scheduled-report scheduler is intentionally two-layer: a pure
  function (`run_due_scheduled_reports`) that does the actual work, and
  a thin APScheduler job (`app/main.py`) that calls it on a timer. Only
  the thin layer is unverified-by-test (you'd need to wait minutes of
  real time to see it fire) — the layer that matters, the actual report
  generation and rescheduling logic, is fully covered by calling the
  function directly with a manipulated `next_run_at`. This split is
  the same pattern as the AI planner (Phase 3): keep the untestable
  wrapper as thin as possible, put the real logic somewhere a test can
  reach it directly.

## Phase 7 additions: enterprise administration

- **API keys piggyback on the existing auth dependency, not a parallel
  one.** `get_current_user` checks whether the bearer token looks like
  an API key (`dlk_` prefix) before attempting a JWT decode, and resolves
  either way to the same `User`. Every existing protected route gained
  API-key support with zero per-route changes — the alternative (a
  separate `get_current_user_or_api_key` dependency used only on some
  routes) would have created two classes of endpoint by accident.
- **Audit logging is allowlisted on purpose.** `record_audit_event()`
  raises `ValueError` for any event type not in the `EVENT_TYPES` set
  rather than silently accepting a typo'd string — the Phase 5 lesson
  (three KPIs silently missing calculators, caught only by a standing
  regression test) generalized into "make the omission loud instead of
  writing a test to catch every possible omission by hand."
- **The admin dashboard computes everything from real aggregate SQL,
  with an explicit list of what it does *not* claim to know** (AI costs,
  system error rates, support tickets — see
  `app/services/admin_stats.py`'s docstring). This mirrors Phase 2's
  data-quality score and Phase 5's KPI engine: every number traces to a
  real query, and gaps are documented rather than estimated.
- **Outbound webhooks reuse Stripe's own signing scheme** (HMAC-SHA256,
  `t=<timestamp>,v1=<hex>`) instead of inventing a new one — a receiving
  server already familiar with verifying Stripe webhooks can verify
  these the same way. Delivery is dispatched after the triggering
  action's own response path succeeds and failures are caught and
  recorded per-subscription, never propagated — the same "the primary
  action must not fail because of a dependent side-effect" shape as
  Phase 6's dashboard widget error isolation.
- **SSO's riskiest code (ID token validation) is delegated to authlib,
  not hand-rolled**, but the token-*exchange* HTTP call is a plain
  `httpx` POST rather than authlib's `AsyncOAuth2Client.fetch_token()` —
  that class turned out to be an `httpx.AsyncClient` subclass with no
  way to inject a test-mocked transport, so using it there would have
  made tests silently perform real, unmocked network calls. See
  `app/services/sso.py`'s module docstring for the full reasoning and
  what's still unverified against a real provider.

## Post-Phase-7 additions: transactional email

- **One `EmailToken` table, not three.** Email verification, password
  reset, and organization invites to not-yet-registered users all need
  the same shape (a one-time, expiring, emailable token) — a `purpose`
  column distinguishes them rather than three near-identical tables.
  This is the same judgment call as Phase 7's single `AuditLog` table
  with an event-type column instead of a table per event category.
- **`EmailSender` is injected via `Depends()`, exactly like
  `get_http_client`** (used for outbound webhooks) — not imported and
  called directly. That's what let tests substitute a plain recording
  object and verify real register → email → verify-token → confirmed
  flows end-to-end, the same testability reason `get_http_client` exists
  rather than webhooks calling `httpx.AsyncClient()` inline.
- **Two dependency variants, not one, for a reason**: `get_email_sender_dep`
  raises a `503` when unconfigured (used where sending the email *is*
  the point of the request — forgot-password, resend-verification), while
  `get_email_sender_optional_dep` returns `None` instead (used where
  email is a best-effort side effect of something that must still
  succeed without it — registration, and inviting an email with no
  account yet, which falls back to its original pre-email-integration
  404). Collapsing these into one dependency would have forced every
  caller to choose between "block the primary action when email isn't
  configured" and "silently skip," when the right choice genuinely
  differs by endpoint.
- **The SMTP client is a direct `smtplib` wrapper, not a provider SDK.**
  Every SMTP provider speaks the same protocol, and this app doesn't use
  any provider-specific feature (templates, click tracking) that would
  justify a dependency on one provider's SDK over plain SMTP.

## Post-Phase-7 additions: more cleaning operations

- **`_apply_table_transformation` is deduplicate's own machinery,
  generalized.** Rather than writing four more ~90-line copies of
  "load every sheet, write a new version, record a Transformation," the
  original `apply_deduplicate` function was refactored into a shared
  helper that takes a `mutate(df) -> (new_df, extra_parameters)`
  callback. Deduplicate itself was rewritten on top of it — covered by
  its existing tests, which still pass unmodified — before the four new
  operations were added the same way.
- **Validation happens before any write, by construction, not by
  convention.** The shared helper loads every sibling sheet's DataFrame
  into memory *before* calling `mutate` on the target sheet, and only
  starts creating the new DatasetVersion/DatasetTable rows and writing
  parquet to storage after `mutate` returns successfully. An operation
  that raises (unknown column, wrong dtype, a column-name collision)
  does so before touching the database — there's no cleanup-on-failure
  logic because there's nothing to clean up.
- **Each operation validates dtype, not just column existence** — mean/
  median require a numeric column, `contains`/normalize-text require a
  text column, calculated-field's arithmetic operators require numeric
  operands and `concat` requires text ones. This mirrors Phase 2's
  original schema-confirmation philosophy: don't silently coerce types,
  reject what doesn't make sense with a specific error.

## Post-Phase-7 additions: S3Storage verification

- **Mock the external API, not your own code.** `tests/test_s3_storage.py`
  runs the real `S3Storage` class against moto, which emulates AWS S3's
  actual request/response semantics, rather than mocking `boto3.client`
  directly and asserting it was called with the right arguments. The
  difference mattered: a unit test mocking boto3 would have let
  `create_bucket(Bucket=...)` "pass" forever, because the bug wasn't in
  this code's logic — it was in which arguments real AWS requires for
  the region this app defaults to. Testing against something that
  actually implements AWS's rules was the only way this surfaced.
- **This still isn't the same as testing against MinIO.** moto is
  AWS-accurate; MinIO is its own implementation with its own (looser, in
  this instance) rules. The bug this caught — a region/
  `LocationConstraint` mismatch — is specifically the kind of thing a
  MinIO-only test pass could miss, since MinIO doesn't enforce it. Worth
  remembering as a general lesson: a convenient local stand-in for a
  real service (MinIO for S3, SQLite for Postgres, a fake SMTP listener
  for a real provider) is not a substitute for testing against the real
  one that the brief actually targets — it narrows the risk, it doesn't
  close it.

## Post-Phase-7 additions: conversation history replay fidelity

- **Display state and replay state are two different columns, on
  purpose.** `AIMessage.content`/`tool_calls` drive the API response and
  the frontend's chat bubbles; the new `replay_messages` column exists
  solely to reconstruct history for the *next* LLM call. Collapsing
  these into one representation would have meant either exposing raw
  Anthropic message-block JSON to the frontend (coupling the UI to the
  LLM provider's wire format) or losing replay fidelity again to keep
  the display format simple. Two columns, two jobs.
- **A turn must always close on an assistant-role message** — this
  wasn't true before the fix (the no-tool-use path simply returned
  without appending anything further; the iteration-limit path ended on
  a tool_result). Anthropic's API rejects two consecutive messages with
  the same role, so a turn that doesn't close on `assistant` would make
  the *next* turn's user message invalid the moment history replay
  actually reconstructs real conversations instead of single isolated
  turns. This is exactly the kind of bug that single-turn tests (all
  that existed before this round) structurally cannot catch — it only
  shows up once two turns are chained together, which is what the new
  cross-turn test in `tests/test_ai_planner.py` does.
- **Old data degrades gracefully, not loudly.** Any AIMessage persisted
  before the `replay_messages` column existed has it as `None`;
  `_history_to_anthropic_messages` falls back to the original flattened
  `{role, content}` representation for those rows rather than requiring
  a backfill migration. A mixed-history conversation (old flattened
  turns followed by new full-fidelity ones) still produces a valid
  message sequence.

## Post-Phase-7 additions: date/currency standardisation and merge/split columns

- **`standardize-column` fixes exactly what profiling.py flags, and
  nothing it doesn't.** `numeric_stored_as_text` and
  `date_stored_as_text` are the two specific issues
  `app/services/profiling.py` has detected since Phase 2 — this
  operation is scoped to correcting precisely those two, not a general
  "clean up my data" button. The date path deliberately requires an
  explicit format from the caller rather than attempting to guess one:
  profiling.py's own `_DATE_PATTERNS` comment already documents that
  DD/MM vs MM/DD is genuinely ambiguous from the text alone, and a
  wrong guess here wouldn't just mis-flag a column (profiling's
  failure mode) — it would silently write wrong dates into every row.
- **Split-column's output width is a property of the data, not a
  parameter.** The number of resulting columns depends on the row with
  the most delimiter occurrences — this can't be known until the
  column is actually inspected, which is why `new_column_names` (when
  given) is validated against the real count rather than accepted at
  face value. This is also exactly why pivot/unpivot (see "What's
  deliberately not built yet" below) are a bigger step than this: their
  output width depends on the *distinct values* in a column, which is
  a more open-ended version of the same problem.
- **Merge-columns casts every source to text before combining.** Unlike
  calculated-field's `concat` (which requires both operands to already
  be text), merge-columns accepts any column types — the brief's
  "merge columns" use case is naturally cross-type (e.g. a numeric
  year + a text quarter into a display label), and there's no
  meaningful arithmetic interpretation to preserve by restricting it.

## Post-Phase-7 additions: second specialist report template

- **Zero new calculation code — purely a template-writing exercise, as
  Phase 5 predicted.** Every KPI in the `residential_property` pack
  reuses a calculator already registered for `commercial_property`
  (`total_rent_roll`, `occupancy_rate`, etc. are generic enough that
  both packs' KPI definitions point at the same functions in
  `app/services/industry_kpis.py`). Building the Residential Property
  Portfolio Report touched zero calculation logic — only the PDF layout
  and the thin router endpoint around it, which is exactly the "now a
  template-writing task, not an architecture problem" Phase 5 left
  in docs/CHECKLIST.md as a prediction to test.
- **New report sections instead of reusing commercial's wholesale.**
  The residential pack has no `category` field, so commercial's
  rent-by-category breakdown has nothing to build from — rather than
  shipping a report with a dead/empty section, the residential report
  gets two sections driven by fields the pack *does* have (tenancy
  expiry, arrears), following the same "only render a section if its
  required fields are actually mapped" conditional pattern the
  commercial report already established for its own sections.

## Post-Phase-7 additions: industry field mapping confirmation

- **One effective-mapping function, not six copies of the same
  fallback logic.** `get_effective_field_mapping()` is the single place
  that decides confirmed-vs-automatic; every caller (KPIs, scenario,
  both specialist reports, scheduled reports, dashboard widgets) was
  updated to go through it rather than each reimplementing "check
  confirmed, else resolve automatically." This matters in practice, not
  just for tidiness: before this, there was no confirmed-mapping
  concept at all, so there was no fallback logic to get inconsistent —
  but had each call site grown its own copy when this landed, a future
  change to the fallback rule would need to be applied in six places
  and could easily miss one.
- **A confirmed mapping is a full replacement, not a patch.** `PATCH
  .../field-mapping` treats the submitted mapping as complete — any
  canonical field the caller doesn't mention goes back to unmapped, not
  "keep whatever the automatic matcher would have guessed for it."
  Mirrors `confirmed_schema`'s existing semantics, and avoids a subtle
  trap: a partial-update interpretation would mean a user who corrects
  one field and saves could unknowingly keep relying on an automatic
  guess for every other field, with no way to tell which fields are
  "reviewed" versus "still just a guess."
- **`compute_widget_value` gained a `table` parameter it didn't need
  before.** Dashboard widgets previously only needed the DataFrame and
  the workspace to compute a KPI value; using the effective mapping
  means they now need the `DatasetTable` too (to read
  `confirmed_field_mapping` off it). A small, mechanical signature
  change, but it's the one call site among the six where the needed
  object wasn't already in scope — everywhere else (`/industry-kpis`,
  `/scenario`, the report generators, scheduled reports) already had
  `table` on hand.

## Post-Phase-7 additions: pivot and unpivot

- **An earlier scoping call reversed on reflection, not silently
  dropped.** Pivot/unpivot were initially left out of the first wave of
  "more cleaning operations" on the stated reasoning that their
  resulting column count is data-dependent rather than fixed — a
  "bigger design question" than the rest. Building split-column in that
  same earlier round had already solved exactly that problem (compute
  the real count from the data, validate against it, don't assume it
  upfront), which made the original reasoning for excluding pivot/
  unpivot stop holding up once examined again. Documented in
  docs/CHECKLIST.md as a reversed scoping decision, not quietly
  revised.
- **Pivot is the one cleaning operation that replaces the column set
  instead of extending or filtering it.** Every other operation built
  on `_apply_table_transformation` either keeps the schema unchanged
  (filter, normalize, standardize) or adds to it (calculated-field,
  split-column) or narrows it by dropping named sources
  (merge-columns). Pivot's output schema is fundamentally a different
  set of columns from its input — that's what "pivot" means, not a
  design compromise — so unlike every sibling operation, nothing about
  the source table's other columns survives into the result.
- **`aggregate_function` is mandatory, not optional, specifically
  because real data has duplicates.** polars' own `pivot()` raises if
  more than one source row shares an index+pivot-value combination
  with no aggregation specified — defaulting to `sum` rather than
  surfacing that as a user-facing error turns "your data has two
  expense rows in the same month and category" from a dead end into
  the normal case.

## Post-Phase-7 additions: persisted group-by

- **One request, multiple aggregations — genuinely more capable than
  the read-only tool it complements, not just a persisted copy of it.**
  Phase 3's `group_aggregate` analytics tool computes exactly one
  aggregation per call. The cleaning operation accepts a list of
  `{column, function, output_name}` entries, so "sum of amount and a
  row count, by category, in one step" is one request instead of two
  separate ones whose results the caller would have to stitch together
  themselves.
- **Group-by and pivot share the same "replaces the schema entirely"
  property**, for the same underlying reason — both operations change
  what a row *means* (one row per group vs. one row per index+pivot
  combination), so nothing about the source table's other columns has
  a well-defined place in the result. This is now a recognized category
  of cleaning operation (alongside "keeps the schema," "extends it,"
  and "narrows it by dropping named sources"), not a one-off exception.

## Post-Phase-7 additions: third specialist report template

- **A compliance caveat earns a different layout treatment than a
  footnote** — it's rendered as a highlighted box directly under the
  report's title, before the data it qualifies, not appended at the
  bottom in 7pt grey text like the methodology note every report
  carries. The brief's own requirement ("compliance caveat ... must be
  displayed prominently") is a layout decision, not just a content
  requirement, and the two other reports' plain-footnote treatment of
  their own methodology notes isn't the right precedent to copy for
  this one.
- **Reused `group_aggregate` in a new mode from inside a PDF generator,
  rather than reimplementing a group-count.** The commercial report
  already called `group_aggregate(df, group_by=..., agg="sum",
  value_column=...)` for its rent-by-category breakdown; the EPC
  distribution section calls the same function with `agg="count"` and
  no `value_column` — the tool already supported it, this is the first
  report to exercise that branch.

## Post-Phase-7 additions: fourth specialist report template

- **Four reports in, and still zero report-specific calculation code.**
  Every one of the four specialist reports is built entirely from
  functions that already existed before any report needed them —
  `compute_kpis` (Phase 5), `group_aggregate` and `time_trend` (Phase
  3). A report generator's job has consistently been "lay out existing
  numbers," never "compute new ones" — the strongest evidence yet that
  the KPI-engine-plus-PDF-layout split from Phase 5 was the right
  architectural boundary, not just a convenient one for the first
  report.
- **The frontend's per-industry branching was refactored from a nested
  ternary into a lookup map once a fourth branch would have made the
  ternary genuinely hard to read** — not preemptively, when there were
  only two or three industries to branch on. Three nested ternaries
  were tolerable; a fourth was the point where the lookup-map
  alternative stopped being a style preference and started being the
  clearer option on its own terms.

## Post-Phase-7 additions: scheduled report email delivery

- **Delivery failure is tracked separately from generation failure.**
  `ScheduledReport` already had `last_run_at`/`last_error` meaning "did
  generation succeed." Adding `last_email_sent_at`/`last_email_error`
  as their own pair, rather than overloading the existing fields, keeps
  "the schedule is broken" (generation failing) distinguishable from
  "the schedule works but mail isn't arriving" (an SMTP outage, a bad
  address) — two operationally different problems a user or admin would
  otherwise have to disambiguate by context. Same shape as
  `WebhookSubscription.last_delivery_error` from Phase 7's webhooks.
- **A send failure never undoes the report.** The PDF is generated and
  stored, the `Report` row committed, *then* email is attempted — not
  the other way around, and not inside the same try/except. If SMTP is
  down, the user still gets a working report in-app; only the email
  attempt itself fails, caught narrowly and recorded without touching
  anything generation already succeeded at. Treating "generate" and
  "notify" as two separable steps (the second optional, the first not)
  is the same shape as how `dispatch_event` fires best-effort webhook
  notifications after a mutation already committed, not inside its
  transaction.
- **`REPORT_TYPE_REQUIRED_INDUSTRY` is one dict, used by two callers.**
  Before this round, only `commercial_property_portfolio` was checked
  against workspace industry at *creation* time; the other three
  specialist report types could be scheduled against the wrong industry
  pack and would silently fail only when the scheduler actually ran
  them. Extracting the report-type-to-required-industry mapping once
  and having both the create-time router check and the run-time
  generator read from it means adding a fifth report type in future
  can't repeat that mistake — there's only one place to update, and
  both call sites update together.
- **Attach the PDF; don't link to it.** The alternative — emailing a
  download link — would need an authenticated download route reachable
  from a cold email link (this app's only existing download endpoint
  requires a logged-in session) or a new magic-token scheme built solely
  for this. Attaching the bytes directly, now that `email.py` supports
  attachments at all, avoids building infrastructure whose only
  consumer would be this one feature.
- **The scheduler resolves `EmailSender` fresh every tick, not once at
  startup.** `get_email_sender()` reads current settings each time
  `_run_due_scheduled_reports_tick` runs, so setting `SMTP_HOST` in a
  running deployment's environment and restarting the process is all
  that's needed to activate delivery — no code change, no separate
  feature flag, consistent with how every other optional integration in
  this app (Stripe, the LLM client, S3) is gated purely on config
  presence.

## Post-Phase-7 additions: distributed scheduler lock

- **A conditional `UPDATE`, not `SELECT` then `UPDATE`.** The lock
  primitive (`app/services/distributed_lock.py`) acquires by running
  `UPDATE scheduler_locks SET ... WHERE id=:id AND (locked_until IS
  NULL OR locked_until < :now)` and checking whether it affected a row —
  never a read followed by a separate write. A read-then-write pair has
  a window between the two statements where a second process could read
  the same "free" state and also decide to acquire; a single UPDATE has
  no such window; the database's own row-level write serialization is
  the mutual exclusion, not application logic layered on top of it.
  This is also the reason the exact same code is trustworthy under both
  SQLite (which this app's tests run against) and Postgres (which
  production runs against) without any Postgres-specific primitive
  (e.g. `pg_advisory_lock`) that would have forced tests to either skip
  the real locking logic or require a real Postgres service just to
  exercise it.
- **A lease (TTL), not a lock held until explicitly released.** A plain
  "locked until released" design fails open into "locked forever" the
  moment a holder crashes or is killed mid-job — exactly the kind of
  failure a distributed lock exists to make unlikely, turned instead
  into the one failure mode that's *worse* than not having the lock at
  all (now nothing runs, rather than something running twice). A short
  lease (240s, under the 5-minute tick interval) means a dead replica's
  stuck lock self-heals within one tick's worth of time, no operator
  intervention required.
- **Lock row created lazily on first use, not seeded by migration.**
  This project's tests build their schema directly from the SQLAlchemy
  models (`Base.metadata.create_all`), bypassing Alembic entirely (see
  `tests/conftest.py`) — a migration-only seed row would simply never
  exist in any test database. Handling first-creation in the
  application code itself (catching the `IntegrityError` from a losing
  race between two processes both trying to create the same row) means
  the exact same function works identically whether the row already
  exists (a long-running production database) or doesn't yet (a fresh
  test database, or a brand-new production deployment's very first
  tick) — one code path, not two.
- **Holder tokens, not a bare boolean, because "did I acquire it" and
  "do I still own it" are different questions.** An earlier version of
  `release_lock` cleared the lock row unconditionally — simpler, but
  wrong: a caller whose acquire attempt *failed* has no way to tell
  "I never held this" from "I'm done with this" if release takes no
  identity, so a buggy or just slightly-too-eager caller could silently
  clobber another replica's active lease. Returning a per-acquisition
  token from `try_acquire_lock` and requiring that same token in
  `release_lock` (which only clears the row when `locked_by` still
  matches) closes that hole entirely — release becomes safe to call
  under any circumstance, including ones the caller didn't anticipate.
- **The whole tick is the unit of locking, not each schedule within
  it.** `run_due_scheduled_reports` acquires the lock once, at the top,
  before even querying which reports are due — not per-`ScheduledReport`
  inside the loop. Locking per-row would still let two replicas each
  grab a *different* due schedule in the same moment and process both
  concurrently, which is fine for correctness (no double-processing of
  any single schedule) but defeats the simpler mental model this design
  aims for: at any instant, at most one replica is inside this function
  at all.

## Post-Phase-7 additions: auth endpoint rate limiting

- **A database table, deliberately not Redis**, even though a
  `redis_url` setting already exists in this app's config. That setting
  was never backed by anything real — its own comment pointed at a
  `app/services/queue.py` that doesn't exist — so building rate
  limiting against it would have meant depending on infrastructure this
  app has never actually proven works, for a feature where correctness
  matters (unlike a background job queue, where a bug mostly just means
  a slow retry). The database is already proven, already configured for
  both SQLite and Postgres, and the volume of rate-limit bookkeeping is
  trivial next to this app's actual data traffic — there's no
  performance case for Redis here that would justify the added
  operational dependency.
- **The same atomic-UPDATE idiom as the distributed scheduler lock,
  reused rather than reinvented.** Both problems reduce to "many
  concurrent actors each trying to update one shared counter/flag
  safely" — the distributed lock needed it for correctness under
  multi-replica concurrency, and rate limiting needs it for the same
  reason under multi-request concurrency from one client hammering an
  endpoint. Writing a second, slightly different "safe concurrent
  counter" pattern alongside the first would have been pure duplication
  of a subtle thing to get right twice.
- **Fixed windows, not a sliding window or a token bucket.** A fixed
  window (e.g. "at most 10 requests in the clock period from
  `:00` to `:05`") is weaker than a sliding window at the window
  boundary — a client could in principle send 10 requests just before
  `:05` and another 10 just after and get 20 through in a few seconds —
  but it needs only one row per (bucket, window) and one atomic
  increment to enforce, versus tracking individual request timestamps
  for a sliding window or replenishment state for a token bucket. For
  defending against sustained brute-force guessing or spam, not against
  a sophisticated attacker gaming a boundary, the simpler primitive is
  the right trade here.
- **A dependency factory, not a decorator or middleware.** FastAPI's
  own dependency system already does exactly what's needed — run before
  the route body, short-circuit with an exception if it fails, compose
  with other dependencies on the same route — so
  `rate_limit_dependency(prefix, max, window)` returning a closure for
  `Depends(...)` fits the framework's own idiom instead of introducing
  a second mechanism (middleware, or a custom decorator) that would
  need its own way to reach the request-scoped DB session FastAPI's
  dependency injection already provides for free.

## Post-Phase-7 additions: httpOnly cookie refresh + CSRF protection

- **Move the credential, not the whole mechanism.** The obvious-looking
  alternative design — switch everything to cookie-based auth, drop the
  `Authorization` header entirely — would have touched `get_current_user`
  (used by every one of this app's 70+ endpoints), every frontend
  `fetch` call, and the API-key auth path that also flows through
  `get_current_user` today. Moving only the refresh token achieves the
  actual security goal (the long-lived, high-value credential is no
  longer in script-readable storage) while leaving everything else —
  access-token auth, API keys — completely untouched. The access token
  itself still passes through JS (it has to, to be attached as a
  header), but it's short-lived and was never the thing sitting
  persistently on disk; the refresh token was.
- **CSRF protection on exactly one endpoint, not a blanket middleware.**
  CSRF defends against ambient-credential requests — ones a forged
  cross-site request can trigger without knowing any secret, because
  the browser attaches the credential (a cookie) automatically. That
  description fits exactly one endpoint in this app: `/auth/refresh`'s
  cookie path, the only place authentication happens with no explicit
  `Authorization` header involved. A global CSRF middleware would have
  protected 69 endpoints that were never exposed to begin with, for no
  security benefit and real complexity cost (every mutating request
  needing a CSRF header, every test needing to supply one).
- **Double-submit, not a server-side CSRF-token store.** The
  `csrf_token` cookie is deliberately non-httpOnly specifically so
  frontend JS can read it back and echo it as a header — its value
  doesn't need to be secret from the page that received it, only
  unreadable by a different origin's page (same-origin policy already
  guarantees that). This needs no server-side session store to check
  tokens against, consistent with this app's existing fully-stateless
  JWT design — adding one would have been new infrastructure solely for
  this feature.
- **A real gap surfaced by actually checking in a browser, not by
  reasoning about the design in the abstract**: a live verification
  pass found a stale pre-migration token still sitting in
  `localStorage` after the code change — nothing read or wrote it
  anymore, but it was still *there*, still a credential, still in
  exactly the storage this feature exists to empty out. The fix
  (`AuthProvider` clearing the old key once on mount) is a one-line,
  one-time migration cleanup, not an ongoing mechanism — the kind of
  gap that a design review would be unlikely to catch, since the
  *design* was correct; only a specific, already-logged-in browser's
  leftover state was wrong.

## Post-Phase-7 additions: billing audit-log gaps closed

- **The schema was already right; only one call site was wrong.** This
  wasn't a design gap that needed new columns or a new query path —
  `AuditLog.organization_id` had been nullable since Phase 7, and
  `GET /users/me/audit-log` already queried by `actor_user_id` alone,
  with no assumption that `organization_id` must be set. The entire gap
  lived in a single `if subscription.organization_id:` guard in the
  webhook handler that only this codebase's own git history would
  explain — worth noting as a general lesson: a "known limitation" is
  sometimes a real architectural boundary, and sometimes just one
  overlooked conditional a grep away from being wrong. Checking which
  one it actually was, before assuming a bigger redesign was needed,
  is what made this a five-minute fix instead of a schema migration.
- **`actor_user_id=subscription.owner_user_id` unconditionally, not
  branched by subscription type.** `Subscription` already guarantees
  exactly one of `owner_user_id`/`organization_id` is ever set (see its
  own docstring) — so passing both fields through unconditionally on
  every call, rather than writing an `if org: ... else: ...` branch,
  lets the model's own invariant do the branching implicitly. One
  fewer place for the two code paths to drift apart later.
- **Finding the second gap came from reading the whole file, not just
  the function the first gap was reported against.** Subscription
  cancellation (`handle_subscription_deleted`, the function immediately
  below the one just fixed) had no audit call at all — a strictly worse
  gap than the first one, and one nobody had flagged. This is the
  general argument for reading a function's neighbors when fixing a bug
  in it: the same category of mistake often clusters in the same file,
  and a five-minute look around after the primary fix is cheap insurance
  against finding the second instance of the same bug class later, by
  accident, in production.
- **Capture `previous_plan_id` before mutating `plan_id`, and test that
  ordering specifically.** The obvious implementation bug here — reading
  `subscription.plan_id` for the audit metadata *after* resetting it to
  `"free"` — would be invisible in a test that cancels an already-free
  account (before and after are identical either way). The regression
  test for this deliberately upgrades to a paid plan first, so a
  capture-order mistake would show up as `previous_plan_id: "free"`
  instead of `"professional"` — a test that only accidentally proves
  the feature at all isn't actually testing the part that's easy to get
  wrong.

## Post-Phase-7: Stripe sandbox verification

Not a code change — the integration was already fully built — but
worth recording how the first real-account verification was actually
done, since the approach itself has design implications worth keeping.

- **Stripe "Sandboxes," not the classic test/live toggle on one
  account.** Connecting the Stripe MCP connector initially exposed only
  the live account (`livemode: true`) — no separate test-mode context.
  Stripe's current account model is a parent account with one or more
  attached sandboxes, each its own distinct account ID with its own API
  keys and product catalog, rather than a single account with a
  test/live switch. Confirmed by navigating the real Dashboard rather
  than assuming: the connector's `list_available_accounts_or_orgs` only
  ever showed the live account, while the Dashboard itself landed in a
  "DataLume Intelligence sandbox" context with its own account ID. This
  is why the actual product catalog was built through the Dashboard UI
  directly rather than through the MCP connector's write tools — the
  connector simply didn't have the sandbox in scope.
- **Stopped before running anything in live mode.** The MCP's
  `livemode: true` result was flagged and confirmed with the user
  before any further action — not assumed safe because it was "only a
  product catalog." Creating real products or Checkout sessions against
  a live account has real consequences (visible to real customers,
  chargeable against real cards); the cost of pausing to confirm is
  negligible next to the cost of guessing wrong on live financial
  infrastructure.
- **`stripe listen --api-key ... --print-secret` instead of `stripe
  login`.** The CLI's own agent guidance recommends this: passing an
  already-known API key skips the interactive OAuth pairing flow
  entirely (which would otherwise need a human clicking "Allow" in a
  browser), and `--print-secret` returns the webhook signing secret
  deterministically for that key — confirmed by calling it twice and
  getting the identical `whsec_...` value both times — without needing
  to keep a listener running just to learn the secret.
- **Price IDs collected via the real Stripe API, not by clicking
  through 8 separate "copy ID" menus.** Once the sandbox's secret key
  was known, a single `GET /v1/prices` call (with the product expanded)
  returned every price's ID, product name, interval, and amount in one
  response — faster and less error-prone than extracting each of 8
  IDs individually from the Dashboard UI, and it's also a second,
  independent confirmation that the Dashboard-created catalog matches
  what the API actually sees.
- **The secret key moved from browser clipboard to `.env` without ever
  appearing as visible text in this conversation.** Stripe's dashboard
  offers "Copy key" (clipboard) as an alternative to visually revealing
  the key; using that and reading the system clipboard (`pbpaste`)
  server-side kept the raw secret out of any screenshot or printed
  output — length and prefix were verified instead of the value itself,
  the same pattern already used for the user-pasted Anthropic API key
  earlier in this project's setup.

## Post-Phase-7: AI analyst verified against a real model

Also not a code change — same as the Stripe sandbox verification above,
this is the second credential-gated integration to move from
"tested against a scripted fake client" to "proven against the real
thing," and the first real evidence that this project's core
AI-grounding design actually works as intended, not just as specified.

- **Two questions, not one, specifically to exercise multi-turn
  replay.** A single question only proves the model can call tools and
  answer sensibly. The second question ("What percentage of that total
  does Acme Ltd account for?") was chosen because answering it
  correctly *requires* the model to actually use turn 1's replayed
  `tool_use`/`tool_result` blocks — "that total" has no antecedent
  without them. The model correctly skipped re-running
  `descriptive_stats` on turn 2 (it already had the total from
  context) and only called `group_aggregate` — behavioral evidence of
  context use, not just a plausible-sounding answer.
- **Figures checked by hand, not just "got a 200."** Every number in
  both responses — £4,500 total, £2,500/£2,000 per tenant, 55.6%/44.4%
  — was verified against the actual uploaded data before calling this
  "working." A model can produce a fluent, wrong answer; only checking
  the arithmetic catches that.
- **This is the project's first real evidence for the grounding design
  itself, not just the API plumbing.** The whole point of routing every
  number through deterministic tool calls (`descriptive_stats`,
  `group_aggregate`, etc.) rather than letting the model free-associate
  over the data is that the model's job becomes "pick the right tool
  and summarize its output," not "do arithmetic" — a narrower, more

  holds in practice, not just in the design.

## Post-Phase-7: SMTP verified against a real mailbox

- **Gmail, via an app password, not a dedicated transactional
  provider.** The design already deliberately avoids any
  provider-specific SDK (`app/services/email.py` is a plain `smtplib`
  wrapper) specifically so any standard SMTP server works — this
  verification pass is the direct payoff of that choice: the fastest
  real account to stand up (an existing Gmail account, 2-Step
  Verification, one generated app password) proved the integration
  works end to end, with zero code written specifically for Gmail.
  A purpose-built provider (Postmark, SES) would exercise the same code
  path identically.
- **A real, observed Gmail quirk, not a hypothetical edge case.**
  An early attempt set `SMTP_FROM_EMAIL` to an address other than the
  authenticated Gmail account. The SMTP transaction itself succeeded
  (no exception, a clean sendmail acceptance) — but Gmail silently
  substituted the authenticated account as the visible sender rather
  than rejecting the send outright. A naive verification that only
  checks "did the API call succeed" would have reported this as
  working when the actual delivered email didn't match what was
  configured. This is exactly why the live-verification standard this
  project holds throughout is reading the actual output (a rendered
  PDF, a real inbox, a real database row) rather than trusting a
  success status code one layer up.

## Post-Phase-7: SSO verified against a real identity provider

Also not fundamentally a code change at first — the OIDC backend
(`app/services/sso.py`, `/sso/login`, `/sso/callback`) already existed
and was the most thoroughly *tested* (against a fake IdP) of the four
credential-gated integrations — but verifying it for real surfaced
enough that it ended up being this round's biggest source of actual
fixes, not just confirmation.

- **The frontend had no page to catch the redirect.** `/sso/login`
  returns a real Google authorization URL, and Google correctly redirects
  back to `OIDC_REDIRECT_URI` (`/sso/callback`) with a `code` and
  `state` — but nothing in `apps/web` was listening there; it 404'd.
  SSO was backend-complete but unreachable from the actual product.
  Fixed by building `apps/web/src/app/sso/callback/page.tsx` (reads
  `code`/`state` from the URL client-side, posts them to
  `/api/v1/sso/callback`, redirects to `/dashboard`) plus a
  `useAuth().completeSso()` method and a "Continue with Google" button
  on `/login` — the same shape as the existing email/password login
  path, not a one-off hack just to make verification possible.
- **Google OAuth app verification can't be read from a tool result — it
  has to be clicked through.** Creating the OAuth client meant: a
  consent screen's "support email" field only ever offers the
  signed-in account or a Google Group it manages (no free text), so the
  app had to be created under the `riaz@datalume.co.uk` account
  specifically rather than patched after the fact; and an
  External+Testing app rejects any login whose email isn't on an
  explicit "Test users" allow-list, discovered only by actually
  attempting a login and watching Google reject it, not by reading
  OAuth docs in the abstract.
- **A real missing-cookie bug, caught only by reloading the page.** The
  callback route built real access/refresh tokens and returned them in
  the response body — which looks completely correct from an API-client
  view (200, valid JWTs) — but never called `set_auth_cookies()`, unlike
  `/auth/login` and `/auth/refresh`. The browser session would have
  looked logged in immediately after the Google redirect and then
  silently logged out on the next page load, with no error anywhere to
  explain why — exactly the kind of bug that only shows up by actually
  reloading the page after logging in, not by checking the login
  response alone. Fixed by adding the same `set_auth_cookies()` call the
  password-login path already makes; confirmed fixed by reloading
  `/dashboard` after a real Google login and seeing the session persist.
- **A real credential-leakage bug in the test suite, caught by rerunning
  it after this verification pass.** 140 of 268 backend tests started
  failing — not from anything in the SSO code itself, but because
  `apps/api/.env` now holds real Stripe/LLM/SMTP/OIDC credentials (every
  one of them verified against a real account this round), and
  `Settings` loads that file by default. The whole suite was built on an
  implicit assumption — "these integrations start unconfigured unless a
  test explicitly turns one on via `monkeypatch`" — that quietly stopped
  being true. The most damaging instance: most of the suite registers a
  test user via a shared helper, and registration sends a best-effort
  verification email that was never wrapped in `try`/`except` — so once
  SMTP was genuinely configured, an ordinary test run started making
  real SMTP connection attempts to Gmail, and any transient failure
  there took down an unrelated test. Two fixes, not one: the
  best-effort email send in `register()` now actually catches failures
  (matching what its own comment already claimed), and
  `tests/conftest.py` now disables `.env` loading for the whole test
  session before `app.main` can import `get_settings()` and cache a
  "real" `Settings()` instance — so the suite only ever sees
  configuration a test explicitly opts into, same as it always assumed.
  This is the same lesson as the Gmail From-address quirk during SMTP
  verification: a clean response at one layer (a 200, a passing test)
  doesn't prove the layer underneath is actually doing what it looks
  like.

  to say that wouldn't just be a re-slice. `residential_property` had a
  genuinely idle field: `maintenance_cost` already feeds one aggregate
  KPI but had never been shown per property anywhere, in this report or
  its sibling.
- **Deliberately didn't reuse the compliance-exceptions report's
  "flagged as an exception" framing for the equivalent missing-data
  section here.** Both reports have a "here's what's missing" section,
  but the underlying honesty is different: a social housing property
  with no inspection date is read as a compliance gap because the pack's
  whole premise is regulatory tracking. A residential property with no
  recorded maintenance spend might just mean nothing broke — this
  pack's fields can't distinguish "never logged" from "never needed."
  Copying the warning-coloured framing from the other report would have
  implied a severity judgement the data doesn't support, so this section
  is worded and styled as informational, not a warning.
- **The generalization from the fifth report's frontend change paid off
  immediately.** Changing the report-button map from
  `Record<industry, generator>` to `Record<industry, ReportDescriptor[]>`
  for social_housing's second report meant this sixth report, on a
  *different* pack, needed zero frontend structural changes — just a new
  entry in an existing list. That's the actual test of whether a
  generalization was premature or correctly timed: the second real use
  needing no further rework.

## Post-Phase-7 additions: dashboard drag-and-drop reorder, add, and remove widgets

- **Scoped to exactly what was documented as missing, not what "drag
  and drop" could maximally mean.** Every mention of this gap in
  docs/CHECKLIST.md said "drag-and-drop layout editor" / "visually
  rearrangeable," never resizing or a freeform 2D canvas — so the
  backend reuses the `position: int` column Phase 6 already had rather
  than adding x/y/width/height fields, and the frontend reflows through
  `rectSortingStrategy` in the existing responsive CSS grid rather than
  building a new grid system. Matching the actual documented promise
  kept this a same-day addition instead of a rearchitecture.
- **The reorder endpoint takes a full ordered id list, not a
  single-widget move.** A `{widget_id, new_position}` pair looks
  simpler, but leaves the server inferring everyone else's shift from
  one delta — exactly the kind of implicit-recompute logic that's
  historically been where this codebase's real bugs hid (the billing
  quota `db.commit()` miss, the scenario-endpoint one). Taking and
  validating the whole new order outright — same ids as currently
  exist, no more, no fewer, no duplicates — means there's nothing to
  infer and nothing can drift.
- **A new runtime dependency (`@dnd-kit`) got an audit check as part of
  landing it, not left for someone to notice later.** `npm audit`
  before and after confirmed every flagged vulnerability traces to
  pre-existing tooling (Next.js, Vitest, Tailwind's PostCSS chain), none
  to the new package — the kind of check that's cheap to do at
  dependency-add time and expensive to reconstruct later if skipped.
- **Verified with an actual pointer drag, not a direct API call
  standing in for one.** The reorder endpoint could be (and was)
  tested directly in the backend suite, but that only proves the API
  contract — it says nothing about whether `dnd-kit`'s sensors,
  `rectSortingStrategy`, and this page's optimistic-update/revert logic
  actually wire together correctly in a real browser. A real drag
  gesture, confirmed via the network panel, a page reload, and the
  database's own `position` column, is the only way to know the whole
  chain — browser interaction through persisted state — actually works.
- **Building the reorder UI surfaced a second gap nothing had
  flagged.** `POST`/`DELETE /dashboards/{id}/widgets*` were real,
  tested backend endpoints since Phase 6 — the frontend simply never
  called either. A reorder feature on a widget set a user can't
  otherwise change is a weaker feature than it looks, so this was
  closed in the same pass: a remove button per card, and an "add KPI
  widget" picker for the four industry packs. The picker reads its
  options from `GET /industry-packs/{id}` — already-existing, tested
  metadata — rather than hardcoding a KPI list in the frontend a second
  time, the same "single source of truth" instinct behind every KPI
  calculation in this codebase sharing one engine.
- **Chart widgets were deliberately left out of the first add-widget UI
  cut, then built as a fully generic form rather than a per-operation
  one.** A KPI widget's config is one field (`kpi_id`) from a fixed
  list; a chart widget's config varies by operation — `group_aggregate`
  needs a group-by column and a value column, `correlation` needs two
  different columns, `time_trend` needs a date column and a bucket-size
  enum. Rather than hand-writing one form per operation (7 forms, each
  needing updates if `app/services/tools.py` ever changes), the form
  reads `GET /tools`' existing `ToolSpec` metadata and renders a field
  per parameter from its shape alone: an `enum` becomes a dropdown of
  those values, an `"integer"` type becomes a number input, and a plain
  `"string"` becomes a dropdown of the table's real column names — true
  for every parameter in every one of the 7 tools today, since this
  registry never uses a bare string for anything but a column
  reference. The payoff of recognizing that pattern: all 7 operations
  are addable through one component, and an 8th tool added to the
  registry later needs no frontend change to become addable too — the
  same "single source of truth" instinct as the KPI picker, just
  applied to a more varied shape of data.
- **The one new backend endpoint this needed was a genuine, slightly
  surprising gap, not a deliberate cut.** Every `/dataset-tables/{id}/*`
  endpoint in this codebase already loads that table internally to act
  on it — deduplicate, normalize-text, confirm-schema, and so on all do
  — but none of them returns the table itself, and no endpoint ever
  existed that did. The chart-widget form needed exactly that (real
  column names for its dropdowns), surfacing a one-line omission:
  `GET /dataset-tables/{id}` reusing the same `get_table_chain_or_404`
  resolver every other endpoint on that path already depends on.
- **General (no-pack) workspaces get their first manual widget-add
  capability of any kind through this, not just a second option.**
  KPI widgets require an industry pack; chart widgets need only a
  table's columns, so this is the only add-widget path available to a
  general workspace — previously limited to whatever "Generate
  Dashboard Automatically" happened to produce, with no way to add
  anything afterward.

## Post-Phase-7 additions: dataset version comparison UI, and a systematic gap sweep

- **Finding the same shape of bug twice by hand is a signal to stop
  looking by hand.** The dashboard add/remove gap and the dashboard
  reorder build both turned up "backend endpoint, zero frontend trace"
  independently, in the same session. Rather than keep spot-checking
  pages for a third instance, the next step was a systematic
  cross-reference: every `@router.get/post/patch/put/delete` across
  every router file against every URL template actually called from
  `apps/web/src/lib/api.ts`. That's a mechanical check a search can do
  exhaustively where manual page-browsing can only sample.
- **The sweep found two gaps bigger than anything built this round —
  and both were deliberately left alone.** Organizations
  (create/list/invite/audit-log — only the invite-*acceptance* half is
  wired) and Webhooks (subscribe/list/delete/test) are each complete,
  tested, multi-endpoint backend features with no frontend trace at
  all. Both are real product surfaces with design questions attached
  (team onboarding UX, whether workspace creation needs an org picker,
  billing-per-org implications) — building either unprompted, the way
  the smaller wiring gaps got closed, would mean making product
  decisions that aren't this session's to make. Flagged explicitly in
  docs/CHECKLIST.md's "Immediate next steps" instead of built.
- **Version comparison was the one sweep result that was purely a
  wiring gap, not a design question.** `POST
  /datasets/{id}/compare-versions` was fully built and tested in Phase
  6; the workspace page's own copy ("N versions · original data
  preserved at every step") already advertised that multiple versions
  exist without ever letting a user act on that fact. No new product
  decision needed — just the missing button and results view, same
  shape as the dashboard widgets fix.
- **Defaulted the version picker to the two most recent versions, not
  the first two.** The most common reason to compare versions is "what
  did the cleaning operation I just ran actually change," which is
  always the newest version against the one before it — defaulting
  there means the common case needs zero clicks before hitting
  Compare, rather than defaulting to v1-vs-v2 and making every user
  reselect for a dataset with more than two versions.
- **Verified against a real, meaningful diff, not an empty one.**
  Uploaded a dataset with a real duplicate row, ran the real
  `/deduplicate` endpoint to produce a genuine second version, then
  confirmed every number in the comparison UI — row count, sum, mean,
  for two different columns — by hand against the source CSV. A diff
  between two identical or near-empty versions would have exercised the
  UI's rendering but proven nothing about whether the underlying
  arithmetic is actually being displayed correctly.

## Post-Phase-7 additions: webhooks UI

- **Confirmed, not assumed, that this was the self-contained gap.** The
  sweep that found this also found Organizations, a structurally
  similar-looking gap (complete tested backend, zero frontend trace).
  The two were sorted by whether closing them required a product
  decision or just engineering — webhooks had none (there's no design
  question in "let a user enter a URL and pick which events to send
  it"), which this build confirmed in practice: it followed the
  existing API keys settings page's pattern directly, no new
  interaction model needed.
- **Reused `WEBHOOK_EVENT_TYPES` as the actual source of the event
  checkboxes, not a copy of the two strings.** A hardcoded
  `["dataset.uploaded", "report.generated"]` in the component would
  have worked identically today and silently drifted the first time a
  third event type was registered server-side — the same "single
  source of truth" instinct as the chart-widget form reading `GET
  /tools` instead of hand-listing operations.
- **A real bug found by deleting something during verification, not by
  reading the diff.** The "secret shown once" banner and the last
  test-delivery result were both left-over component state with no
  code path clearing them on delete — so deleting a webhook left its
  secret and stale test result visually attached to a subscription that
  no longer existed. This is the same category of bug the project has
  hit before (stale UI state outliving the thing it describes) and the
  same lesson each time: the way to catch it is to actually perform the
  destructive action during verification and look at what's left on
  screen, not to read the component and reason about what *should*
  happen.
- **Verified the failure path with a real failure, not a mock.** A
  second webhook pointed at `https://httpbin.org/status/500` to confirm
  the UI's "Test delivery failed: HTTP 500" branch actually renders
  from a genuine non-2xx response — the same principle as verifying a
  success path against `https://httpbin.org/post`: a feature's error
  handling isn't proven until something has actually failed through it.

## Post-Phase-7 additions: organizations UI

- **A real investigation changed the actual scope of the "needs product
  decisions" flag, rather than the flag just being wrong.** Organizations
  was deliberately left unbuilt earlier specifically because it looked
  like it needed new product/UX answers (does workspace creation need
  an org picker, how does billing interact with an org). A dedicated
  read-only investigation before writing any code found both answers
  already existed and were already tested: `POST /workspaces` already
  accepted `organization_id`, and `Subscription` was already dual-keyed
  (user XOR org) with membership-gated billing endpoints. The flag
  wasn't a misjudgment — it correctly identified open questions — it's
  that the questions turned out to already be answered in code nobody
  had read yet, which only a real investigation could have surfaced
  over guessing.
- **Deliberately didn't build an org-aware billing/pricing page in this
  pass**, even though the backend already supports it. Scope
  discipline: this round closed the one actual gap (no member-listing
  endpoint) and wired the two already-built capabilities (org-scoped
  workspace creation, org membership → shared access); a billing UI
  that lets a user pick which organization's plan to manage is its own
  separate surface with its own design questions (how does an upgrade
  flow present multiple billable entities?) that this round's
  investigation didn't resolve.
- **The new `GET /organizations/{id}/members` endpoint is readable by
  any member, not just owner/admin** — deliberately mirroring the
  `require_workspace_access` (any member reads) vs.
  `require_workspace_write_access`/`require_org_manager` (restricted
  roles for writes/governance) split this codebase already uses
  consistently for workspaces. Seeing who else is in your own
  organization isn't a governance action; inviting, auditing, and
  billing are.
- **A real bug — not a hypothetical one — from relying on a response
  shape instead of verifying it.** The invite success message assumed
  the invite endpoint's response included the invitee's email, because
  the *list members* endpoint (built in the same session) does. It
  doesn't — `MembershipOut` (what the invite endpoint actually returns
  for an existing user) only ever had `user_id`. This produced a
  working feature with a cosmetically broken confirmation message
  ("undefined added as analyst"), caught only by actually clicking
  Invite and reading the screen during verification — exactly the kind
  of bug a type system can't catch when two different response shapes
  get collapsed into one TypeScript interface that's only true for one
  of them. Fixed by splitting the type in two and using data the
  frontend already had locally (the email just typed) instead of
  trusting the response to echo it back.
- **Verified the feature's actual point, not just its CRUD surface.**
  Creating an org, inviting someone, and seeing a member list all
  passing doesn't prove organizations *do* anything — the real claim is
  "members of the same org share workspace access." Proven by logging
  in as a second real account that never created the workspace in
  question and confirming it was visible and fully usable, which is the
  one assertion that actually distinguishes this feature from a
  no-op settings page.
